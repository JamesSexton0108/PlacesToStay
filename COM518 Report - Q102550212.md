Part A -- Develop a very simple REST API

Before anything, we must set up the basics of the server API. This
includes imports for Express, ViteExpress and Better Sqlite3. These
imports will be utilised throughout the development of part A so need to
come first. We also need to create these 3 variables:

const app = express();

const PORT = 3000;

const db = new Database("placestostay.db")

1\. The first requirement is to allow users to retrieve all
accommodation options in a given location. In order to do this, a GET
HTTP request method should be used, as we are just reading from the
database, not altering it. We can treat accommodation as a resource and
location as a filter in the URL, creating a route that looks like:

/accommodation/location/:location

This structure means that the desired location can be specified
dynamically through the URL. Using express, this can be implemented with
app.get(), with the location parameter being accessed using
req.params.location. The relevant data can then be accessed using an SQL
query in the form "SELECT \* FROM accommodation WHERE location = ?
COLLATE NOCASE". This query is then returned in the JSON format, which
can then be parsed into a more easily readable format in later tasks.

2\. The second requirement follows largely the same structure as the
first, utilizing app.get() with multiple parameters in order to filter
accommodation in a given location by type. Another SQL query is also
used to achieve this, coming in the form "SELECT \* FROM accommodation
WHERE type = ? AND location = ? COLLATE NOCASE".

3\. The third requirement will need to include an app.post() request as
we are inserting data into the database. We will use a separate insert
statement and update statement, with the insert adding new entries into
the bookings table and the update updating the dates table to reflect
the new availability based on the number of people being inserted into
the new booking. The insert will look something like "INSERT INTO
acc_bookings(accID, thedate, userID, npeople) VALUES(?,?,?,?)" and the
update will look like "UPDATE acc_dates SET availability =
availability - ? WHERE accID = ? AND thedate = ?".

Part C -- Adding simple error-checking

6\. For the simple error checking in part C, I will make it so that in
the /booking post request, there will be simple error checking before
the database is updated where accID, thedate and npeople must not be
blank. If one is blank, the server will return an HTTP 400 Bad Request
status code along with a json error message explaining which one is
missing. If all are there, then the booking will work as usual and the
server will return a 200 OK status code. The bookAccommodation function
in App.tsx will now check the returned HTTP code and then display a
relevant message to the user.

Part D -- Adding a map

7\. First, a map will need to be added utilising leaflet. This is done
by importing leaflet and then creating a map object. We will use useRef
from React to hold a reference to the map, which is important as it
means the map will not be recreated every render, it will just stay

Part E -- Logins and sessions

8\. To implement a login system, the packages express-session and
express-session-better-sqlite3 will need to be installed. These allow us
to manage session creation and store session data on the server
respectively. We will also need to create a type declaration file for
express-session-better-sqlite3 as it does not have a corresponding
\@types/ package. This will need to be in a "types" folder and will also
require tsconfig.json to have its paths option configured to look inside
the types folder. Additionally, module augmentation will need to be used
to extend express-session\'s SessionData interface with a username
property, so that req.session.username can be used without errors. This
will be placed in a separate file (session.d.ts) and also added to
tsconfig.json. Three routes need to be added to the server. The POST
/login route receives a username and password from the client, checks
them against the acc_users table in the database using get(), and if
valid, stores the username in req.session.username and returns it as
JSON. If the credentials are invalid, a 401 Unauthorized response is
sent. The GET /login route will return the currently logged-in username,
or null if no session exists, which allows the frontend to restore login
state when the page is reloaded. The POST /logout route destroys the
session. On the client side, a username state variable will be added to
the App. A useEffect will run once, sending a GET request to /login to
check whether the user already has an active session -- in order to
maintain login status across page reloads. Either a login form or a
\"Logged in as\...\" message with a logout button is rendered, depending
on whether username is null. Middleware will also be added to protect
POST routes from unauthenticated users, returning a 401 if a request is
made without an active session, with an exemption for the /login route
itself so users are not blocked from logging in.

Part G -- More advanced tasks

10\. Two additional checks will be added to the POST /booking route on
the server, before the booking is inserted into the database.

The first check will verify that the requested date is not in the past.
The dates in the database are stored as numbers in YYMMDD format (e.g.
260601 for 1st June 2026). Today\'s date will be constructed in the same
format using JavaScript\'s Date object, and if the requested date is
numerically less than today\'s date, the server will return a 400 Bad
Request response with an appropriate error message in the JSON body.

The second check will query the acc_dates table for a row matching the
requested accommodation ID and date. If no matching row exists, or if
the availability value for that row is less than the requested number of
people, the server will return a 409 Conflict response, again with a
descriptive error message in the JSON body. A 409 is appropriate here as
the request is valid in itself but conflicts with the current state of
the resource.

11\. For task 11, the booking will be changed so that the user can now
enter a date and number of people for the accommodation instead of it
being hardcoded. This will be done using a \<input type="date"\> for
date selection and a \<input type=\"number"\> for the number of people.
Today's date will be put as a minimum option to prevent dates in the
past being selected. A dates state object and npeople state object will
be created to track these values independently for each accommodation
showing in the results list. When the book button is clicked, the date
value will be converted to the YYMMDD format to match the database.
